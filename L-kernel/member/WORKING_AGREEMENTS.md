# L-kernel / MB 讨论记录与迁移地图

这是 Ethan 在本轮讨论中的产品决定与实施工作记录，不是新的节点、接口、数据库或权限权威。实现前仍以现有 SFL 节点模型、数据库事实和根 `LAW.md` 的有效规则核对；未完成项不得写成已交付。

## Ethan 明确强调的迁移禁令

**严禁为了建设 L-kernel 而重写、仿写、重新想象现有会员业务逻辑；严禁顺手乱改原有业务源码。** 这是本次迁移的最高优先级工作边界，不是“代码风格建议”。错写原逻辑可能改变会员归属、父链、订单和权限，造成实际业务损失。

执行顺序固定为：只读核对原实现与依赖 → 标注原文件及相关 SQL → **按业务职责切割原代码，把被切出的原逻辑放入内核** → 用原测试与数据事实证明行为等价 → 原调用点仅改为薄委托 → **之后**才按 Ethan 已确认的新规则作定点修改并单独验收。切割不是整文件搬家，更不是重写。未经这一步，不新造替代算法、替代仓库、替代节点模型或“看起来更好”的业务流程。确有原代码没有的能力（例如跨 ST 资料共享）时，先标记为新增缺口，不伪装成源代码切割。

允许触碰旧源码的范围，仅限该片切割所需的导入、薄委托与明确批准的规则差异；每次列出原路径、新路径及行为差异。不得批量重构、提前删除运行路径或改动登录、订单、权限、VI。切割与新规则修改分两次可核对的验收，不能混在同一份无法分辨的改动中。

## 已明确的目标

1. 本地正本是 `/Users/Ethan/Desktop/zdt-next`，工作分支 `codex/L-kernel`；不切走、不移动桌面主目录。L-kernel 放在此仓库主轴，先完成 MB 会员内核，再由 L0（zhudatuan）、L1（hbbtzn）、L2（H6）接入；模拟测试不等于三处真实继承。
2. **按职责切割现有源代码，不另写一套取代它。** 每一片先标明原文件与数据库事实，把可共用的原逻辑原样切出，原调用只留薄适配；同一事实不能有两个写入源。新规则修改必须在切割和等价验证之后单独进行，不借切割做无关重构。
3. L-kernel 承载既有“四流合一”及 SFL 节点链的共用能力；L0～L5 是企业／店铺侧切片，L6～L11 是 MB 会员侧切片，L-1～L-5 是 SU 供应链侧切片。节点、父链、升级及交易事实沿用现有权威，不在这里造第二套节点模型。四流的逐字段语义仍须逐段对照原代码，不能靠本记录重新定义。
4. 各 L-kernel 实例的身份、Realm、账号、密码、数据和 OP 实例相互独立；复用一份实现，不互继权限。目标包含独立物理数据库，但现有 L0/L1/H6 是否均已达到物理隔离，必须单独验收，不能仅凭配置推断。
5. OP 是与 L-kernel 平行的管理体系，不是 MB 的一种等级。每家 ST 都有自己的 Owner，可有高级管理员和普通管理员；角色可以变化，OP 身份码不随之变化。L1 开设 L2 时，L2 必须有自己的初始 Owner，此后可转让。跨店 OP 可经客服中心通信，但留言不能转成对对方店铺的增删改查或管理权。
6. ST 是店铺／节点身份，OP 是管理身份，MB 是消费者身份，SU 是供应链身份。一个手机号可以对应不同店铺的多份 OP／MB 等身份；手机号只是辅助联系字段，不是身份主键或权限来源。当前产品不允许把同一手机号当作不同自然人的共享账号；换号、号码回收的详细处置留待后续。
7. 身份码全域唯一、一次性分配、作废不回收。已讨论的目标长度：OP、ST、SU 各六位，MB 八位。MB 采用 **4+4**：唯一全域库只分配每家 ST 的前四位；后四位在会员原归属 ST 的数据库分配。共享到别店不重发 MB 码。易混淆的字母 O/I/L 不使用，保留数字 0/1；具体字符表要从原编码实现核对后作最小调整。
8. 现有六位 MB 展示码是旧编码：正式切换时直接失效并删除旧 MB 生成／映射路径，不做兼容查询、翻译或回填。OP 旧实现独立处理；“动态会员码挑战”若用于临时核验，不等于永久身份码，不能因同名而误删。当前新八位码尚未接入，旧运行路径也尚未删除。
9. 身份码只用于展示、查阅、核对和复述存在的身份，不是登录凭据、操作目标、权限令牌或跨店数据入口。读写业务关系仍用完整 Membership ID，并在原归属 ST／Realm 依据现有规则查询；不让短码参与认证、授权或写命令。不得新增审批、验证码、Step-Up 等安全门禁来“修复”标识问题。
10. 登录的目标流程是先选 ST，再在该 ST 登录；如果有多份可用身份，再选具体身份。OP 与 MB 分开登记；有 OP 不自动拥有 MB。一个手机可在多个 L-kernel 使用，账号密码等独立。登录本身不吸入 MB 领域核心，变更须单独验收。
11. ST 间 MB 资料／会员关系可以在从属、买卖等业务关系下，经双方约定共享**明确选中的固定名单**并可撤回；后续新会员不自动加入。来源 ST 和接收 ST 的名册均标注共享方向。接收店可查获授权的资料、识别原 MB，不强迫重新注册，但 MB 原码不变。订单永远属于实际购买的店铺，不共享旧订单，也不把上级店的订单显示成下级店订单。已在接收店注册另一份 MB 时，不凭手机号自动合并两份身份或历史关系；合并须用户选择，具体数据规则尚未实现。
12. L6～L11 会员申请开店时，新增 L0～L5 的店铺／管理身份，原 MB 码与原历史不作废。新店**引用**原 MB 后续关系，不改写原父链、L 等级或历史订单；现有开店 SQL 直接改造原 MB 节点，与此新目标不同，不能当作已实现或等价切割。
13. 购买、收款、发货、退货的四流事实原则上自动推进；需 OP 介入的节点处理例外，不把人工审核变为每笔交易必经步骤。ST 节点本身不直接获得人工管理 MB 的权限。手机／微信匹配与换绑属于另一个业务流程，不纳入本次 MB 内核迁移。
14. 前后端分离、VI／布局／主交互保持原样。订单、地址、导入、登录和前端展示留在各自模块；可选业务片可拔除而不影响 MB 基础事实。不新增全局状态、大型依赖、第二套权限权威或无关安全门禁。节点差异只用既有权威节点数据及必要薄配置，不复制三份实现，也不假定一个 JSON 文件能替代数据库事实。
